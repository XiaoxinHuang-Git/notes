## 11-07 PDO 关闭模拟预处理后，三个行为会变

**结论**：生产环境把 `PDO::ATTR_EMULATE_PREPARES` 设为 `false`，但改造时要注意占位符复用、LIMIT 绑定、返回类型三处差异。

**默认值**：PDO 连接 MySQL 时该项默认为 `true`。此时参数由 PDO 在客户端转义后拼进 SQL，本质仍是字符串拼接，只是转义交给了驱动。

```php
$pdo = new PDO($dsn, $user, $pass, [
    PDO::ATTR_ERRMODE          => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_EMULATE_PREPARES => false,   // 走 MySQL 服务端预处理
]);

// 查看当前值
var_dump($pdo->getAttribute(PDO::ATTR_EMULATE_PREPARES));
```

**差异一：同名占位符不能复用**

```php
// emulate = true：正常
// emulate = false：SQLSTATE[HY093] Invalid parameter number
$stmt = $pdo->prepare('SELECT * FROM orders WHERE buyer_id = :uid OR seller_id = :uid');
$stmt->execute([':uid' => 1001]);
```

原生协议只支持位置参数，PDO 需要把命名参数重写成 `?`，同名参数会超出绑定数量。改成两个参数即可：

```php
$stmt = $pdo->prepare('SELECT * FROM orders WHERE buyer_id = :buyer OR seller_id = :seller');
$stmt->execute([':buyer' => 1001, ':seller' => 1001]);
```

**差异二：LIMIT 必须显式按整数绑定**

```php
// emulate = true 时若按字符串绑定，最终拼成 LIMIT '10'，语法报错
$stmt = $pdo->prepare('SELECT * FROM orders ORDER BY id DESC LIMIT :n');
$stmt->bindValue(':n', 10, PDO::PARAM_INT);
$stmt->execute();
```

`execute([10])` 在模拟模式下会按字符串处理，这里必须用 `bindValue` 指定 `PARAM_INT`。

**差异三：返回类型不同**

开启 `mysqlnd` 且关闭模拟预处理时，整型列返回 `int`、浮点列返回 `float`；模拟模式下所有列都是字符串。依赖严格类型比较的代码（如 `===`）要提前确认。

**排查建议**：连接串上显式写死这个参数，不要依赖 php.ini 默认值——不同环境的默认值可能不一致，问题只在生产暴露。

## 11-07 proxy_pass 带不带尾斜杠，转发路径完全不同

**结论**：`proxy_pass` 后面写不写 URI（含末尾那个 `/`），决定了 nginx 是原样透传请求路径，还是把 location 前缀替换掉。排查上游 404 时先看这一处。

**原因**：nginx 文档的表述是——`proxy_pass` 指定了 URI 时，请求 URI 中与 location 匹配的那部分会被替换成该 URI；没有指定 URI 时，请求 URI 原样转发给上游。

```nginx
# 情况一：只写 host:port，没有 URI，原样透传
location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
# /api/users -> http://127.0.0.1:8080/api/users

# 情况二：带一个 /，相当于剥掉 location 前缀
location /api/ {
    proxy_pass http://127.0.0.1:8080/;
}
# /api/users -> http://127.0.0.1:8080/users
```

**最容易踩的坑**：location 写 `/api/`，`proxy_pass` 却写成不带尾斜杠的 `http://127.0.0.1:8080/api`。此时匹配到的 `/api/` 被替换成 `/api`，剩下的 `users` 直接贴上去：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080/api;   # 少了一个斜杠
}
# /api/users -> http://127.0.0.1:8080/apiusers
```

表现是连接正常、上游返回 404，上游 access log 里的 URI 变成 `/apiusers`。规则很简单：两边都带斜杠，或者两边都不带，不要混着写。

**正则 location 不能带 URI**：下面这种写法启动时直接失败：

```nginx
location ~ ^/api/(.*)$ {
    proxy_pass http://127.0.0.1:8080/$1;
}
```

报错信息是 `"proxy_pass" cannot have URI part in location given by regular expression`。需要改路径就先用 `rewrite ... break` 把 URI 改好，`proxy_pass` 里只留 `http://127.0.0.1:8080`。

**关联配置**：上游返回 302 且 `Location` 里带内网地址时，浏览器的跳转会指向错误地址。保持默认的 `proxy_redirect default;` 会按 `proxy_pass` 里的上游地址做替换，但它只在 `proxy_pass` 不带 URI 时生效；带 URI 的场景要显式写 `proxy_redirect http://127.0.0.1:8080/ /;`。

**验证方式**：改完先 `nginx -t` 确认语法，再 `curl -i http://127.0.0.1/api/users`，对照上游 access log 里的真实 URI，比在浏览器里猜快得多。

## 11-08 字符串列与数字比较会让索引失效，还会多匹配出数据

**结论**：`varchar` 列和数字常量比较时，MySQL 会把列的值转成浮点数再比，索引用不上；同时 `'13800138000abc'` 这类脏数据也会被当成 `13800138000` 命中。条件里的常量类型必须和列类型一致。

**复现**

```sql
CREATE TABLE t_user (
  id    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  phone VARCHAR(20)   NOT NULL DEFAULT '',
  PRIMARY KEY (id),
  KEY idx_phone (phone)
) ENGINE=InnoDB;

-- 两种写法，语义上"看起来"一样
EXPLAIN SELECT id FROM t_user WHERE phone = '13800138000';
EXPLAIN SELECT id FROM t_user WHERE phone = 13800138000;
```

第一条 `type=ref`、`key=idx_phone`；第二条 `type=ALL`、`key=NULL`，全表扫描。

**原因**：比较时的转换方向由列类型决定。列是字符串、常量是数字，规则是把列转成 double，等价于 `CAST(phone AS DOUBLE) = 13800138000`。列上套了函数，索引自然失效。MySQL 5.7 与 8.0 在这一规则上一致。

**连带问题：结果也不对**。字符串转数字是宽松截断的，能解析出前面的数字就取，后面忽略：

```sql
SELECT '13800138000abc' + 0;   -- 返回 13800138000，同时抛 Truncated incorrect DOUBLE value 警告
```

所以 `WHERE phone = 13800138000` 会连带查出 `'13800138000abc'`、`'13800138000 '` 这类记录，业务上很难发现。

**反方向没问题**：`id` 是 `BIGINT`、常量写成 `'1001'`，被转换的是常量，`idx` 照常使用。判断依据是"转换的是不是列"，不看常量怎么写。

**同类写法**：让列参与运算或套函数，效果一样。

```sql
-- 失效
SELECT * FROM t_user WHERE DATE(created_at) = '2026-11-08';

-- 改成范围，可走 idx_created_at
SELECT * FROM t_user WHERE created_at >= '2026-11-08 00:00:00'
                       AND created_at <  '2026-11-09 00:00:00';
```

**排查**：`EXPLAIN` 看 `type` 是否为 `ALL`、`key` 是否为 `NULL`；怀疑隐式转换时，执行原查询后紧跟 `SHOW WARNINGS`，出现 `Truncated incorrect DOUBLE value` 基本可以确认。

**落地**：参数绑定要传正确的类型，`int` 字段别从请求参数里直接拿字符串塞进去；把"列类型与条件常量类型一致"写进 review 清单。

## 11-09 Redis 分布式锁的三个正确姿势

**结论**：`SET key value NX EX seconds` 是唯一正确的加锁原子操作；释放时用 Lua 脚本保证 "比较-删除" 原子性；业务过期时间必须比锁过期时间短。

**错误写法一：先 EXISTS 再 SET**

```php
// 典型的竞态条件
if ($redis->exists($key)) {
    return false;
}
$redis->set($key, $value);   // 两个进程同时通过了 exists，都 set 成功
```

**错误写法二：SETNX 后单独 EXPIRE**

```php
if ($redis->setnx($key, $value)) {
    $redis->expire($key, 30);  // 进程在这一行挂了，锁永不过期
}
```

**正确写法：一条命令搞定**

```php
// PHP
$token = bin2hex(random_bytes(16));
$acquired = $redis->set($key, $token, ['nx', 'ex' => 30]);
if (!$acquired) {
    return false;  // 没抢到锁
}

// 业务逻辑...

// 释放锁：Lua 脚本保证原子性
$script = <<<'LUA'
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
LUA;
$redis->eval($script, [$key, $token], 1);
```

```go
// Go
func TryLock(ctx context.Context, rdb *redis.Client, key string, ttl time.Duration) (string, bool, error) {
    tokenBytes := make([]byte, 16)
    rand.Read(tokenBytes)
    token := hex.EncodeToString(tokenBytes)

    ok, err := rdb.SetNX(ctx, key, token, ttl).Result()
    if err != nil {
        return "", false, err
    }
    return token, ok, nil
}

func Unlock(ctx context.Context, rdb *redis.Client, key, token string) error {
    script := redis.NewScript(`
        if redis.call('get', KEYS[1]) == ARGV[1] then
            return redis.call('del', KEYS[1])
        else
            return 0
        end
    `)
    return script.Run(ctx, rdb, []string{key}, token).Err()
}
```

**关键要点**：

1. **value 必须是唯一标识**（随机字符串或 UUID），不能是固定值，否则 A 拿了锁过期后 B 拿了同一把锁，A 再 DEL 会把 B 的锁删掉
2. **释放必须用 Lua**，GET + DEL 之间如果锁刚好过期并被别人抢走了，DELETE 会删错
3. **业务时间 < 锁过期时间**，但锁过期时间也不能太长——进程崩溃后其他进程要等很久才能拿到锁
4. **Redis 集群注意**：锁的 key 和 value 应该在同一个 slot（用 hash tag 强制），`SET NX EX` 在集群模式下是原子的但仅限单 key 操作

## 11-09 Go 中 defer 和 named return 一起用时会修改返回值

**结论**：defer 里能读到和修改 named return；如果函数用的是匿名返回值，defer 里改了也白改。排查返回值不符合预期时先看这一点。

**复现**

```go
func namedReturn() (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("panic recovered: %v", r)  // 能改 named return
        }
    }()
    panic("something broke")
}
// namedReturn() 返回 error("panic recovered: something broke")

func anonymousReturn() error {
    defer func() {
        if r := recover(); r != nil {
            err := fmt.Errorf("panic recovered: %v", r)  // 改的是局部变量
            _ = err
        }
    }()
    panic("something broke")
}
// anonymousReturn() 返回 nil（因为匿名返回值默认零值）
```

**另一个坑：defer 的参数在注册时就求值了**

```go
func example() {
    i := 0
    defer fmt.Println(i)  // 打印 0，不是 3
    i++
    i++
    i++
}
```

defer 语句里的 `i` 在 defer 注册那一刻就被求值为 0 了。如果想打印最终值：

```go
defer func() {
    fmt.Println(i)  // 打印 3
}()
```

**总结**：

- 需要 defer 修改返回值 → 用 named return
- 不需要修改返回值 → 用匿名返回值，语义更清晰
- defer 传参数和闭包取变量是两个不同的求值时机

## 11-09 proxy_pass 后转发到上游时，Host 头可能不是你以为的那个

**结论**：默认情况下 nginx 会把客户端原始请求的 Host 头原样传给上游，上游可能拿到 CDN 域名或客户端自定义的 Host，而不是你内部服务期望的那个。

**问题场景**

```nginx
server {
    listen 443;
    server_name api.example.com;
    
    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}
```

上游 Go 服务里 `r.Host` 拿到的是 `api.example.com`。如果通过内网 IP 或另一个域名也能访问这个上游服务（比如 `http://internal-service.local/`），而上游根据 Host 做了路由或签名校验，就会出现"用 CDN 域名访问 OK，用内网域名访问不 OK"的诡异现象。

**修复方案：显式覆盖 Host 头**

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;          # 用客户端原始 Host
    # 或者明确指定
    proxy_set_header Host internal-service.local;
    # 或者用上游的 host
    proxy_set_header Host $proxy_host;    # 即 127.0.0.1:8080
}
```

**常用的 proxy_set_header 清单**：

```nginx
proxy_set_header Host              $host;           # 客户端 Host
proxy_set_header X-Real-IP         $remote_addr;    # 客户端真实 IP
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;  # 经过的代理链
proxy_set_header X-Forwarded-Proto $scheme;         # http 还是 https
proxy_set_header X-Forwarded-Host   $host;           # 原始 Host
proxy_set_header X-Forwarded-Port   $server_port;    # 客户端访问的端口
```

这些头在上游服务里用于获取真实客户端信息，尤其是在做 IP 限流、日志记录、回调 URL 生成时不能少。Laravel / Express / Gin 都有内置方法读这些头。

## 11-09 ThinkPHP 5.x 的 whereRaw / query 闭包没转义，直接拼用户输入就是 SQL 注入

**结论**：ThinkPHP 的 `whereRaw()` 和 `DB::query()` 确实支持参数绑定，但闭包写法和部分链式方法会绕过预处理。安全扫描报 ThinkPHP 注入时，十有八九是在这些地方。

**危险写法**

```php
// 危险一：whereRaw 直接拼
$keyword = $_GET['q'];
User::whereRaw("name LIKE '%{$keyword}%'")->select();

// 危险二：query 直接拼
$table = $_GET['table'];
DB::query("SELECT * FROM {$table}");

// 危险三：order / field 支持数组但不支持参数绑定，拼字符串等于裸奔
$sort = $_GET['sort'];
User::order($sort)->select();   // order('id; DROP TABLE users')
```

**安全写法**

```php
// whereRaw 用 ? 占位符
User::whereRaw('name LIKE ?', ['%' . $keyword . '%'])->select();

// query 用参数绑定
DB::query('SELECT * FROM users WHERE id = ?', [$id]);

// order / field 用白名单
$allowed = ['id', 'name', 'created_at'];
$sort = in_array($sort, $allowed, true) ? $sort : 'id';
User::order($sort)->select();

// 表名/列名用 whitelist，不能参数绑定
$allowedTables = ['users', 'orders', 'products'];
$table = in_array($table, $allowedTables, true) ? $table : 'users';
DB::table($table)->select();
```

**排查清单**：全仓库搜 `whereRaw`、`query(`、`execute(`、`order(`、`field(`、`table(`，看是否有 `$_GET` / `$_POST` / `input()` 的用户输入直接拼进参数。

## 11-10 Nginx HTTPS 配置和 HTTP 强制跳转的标准写法

**结论**：`listen 443 ssl http2` 配 TLS 证书 + 一个 `listen 80` 的 server 块做 301 跳转是最标准的方案。不要在同一个 server 块里同时监听 80 和 443。

**TLS 证书文件**：通常是两个文件——`fullchain.pem`（证书链，从域名证书到 CA 根）和 `privkey.pem`（私钥）。如果只有一个文件，可能是把两者拼在一起了。

```nginx
server {
    listen 80;
    server_name example.com www.example.com;
    # 永久跳转到 HTTPS
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name example.com www.example.com;

    # 证书路径（以 certbot 为例）
    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    # TLS 版本和加密套件（A+ 评级配置）
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;
    ssl_prefer_server_ciphers on;

    # 会话缓存，减少 TLS 握手开销
    ssl_session_timeout 1d;
    ssl_session_cache shared:SSL:50m;
    ssl_session_tickets off;   # 开了 session cache 就关掉 tickets

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
    }
}
```

**安全响应头**：HTTPS 站点必须配 HSTS，否则浏览器在第一次访问时仍可能被中间人攻击。

```nginx
server {
    # ... listen 443 ...
    
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
}
```

`always` 关键字很重要——它让 nginx 对所有响应都加这个头，包括 4xx/5xx。没加的话错误响应就没 HSTS 了。

**HTTP → HTTPS 的其他写法**：

```nginx
# 方式一：return 301（推荐，最短路径）
listen 80;
return 301 https://$host$request_uri;

# 方式二：rewrite（比 return 稍慢，需要匹配 location）
listen 80;
rewrite ^ https://$host$request_uri? permanent;

# 方式三：按 URI 条件跳转（某些路径保留 HTTP 时用）
listen 80;
if ($request_uri !~* ^/api/internal/) {
    return 301 https://$host$request_uri;
}
```

**证书续期**：Let's Encrypt 证书 90 天过期。certbot 会自动加 cron 任务检查续期，续期后 reload nginx：

```bash
# 检查续期情况
certbot renew --dry-run

# 自动 reload nginx
certbot renew --post-hook "systemctl reload nginx"
```

## 11-10 MySQL 慢查询完整排查步骤

**结论**：慢查询排查分三步走——先开启慢日志拿到 SQL，再 EXPLAIN 看执行计划，最后针对性优化索引或改写 SQL。别一上来就调参数。

**第一步：开启慢查询日志**

```sql
-- MySQL 5.7 / 8.0
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;           -- 超过 1 秒记录
SET GLOBAL log_queries_not_using_indexes = 'OFF';  -- 全表扫描也记录（生产慎开，量太大）
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';

-- 以上是临时生效，重启后失效。永久生效写到 my.cnf
-- [mysqld]
-- slow_query_log = ON
-- long_query_time = 1
```

查当前状态：

```sql
SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';
```

**第二步：用 EXPLAIN 看执行计划**

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 123 AND status = 1 ORDER BY created_at DESC;
```

重点看 `type` 列：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL`（越靠右越慢，`ALL` 是全表扫描）。

`Extra` 列里的关键词：

- `Using index`：覆盖索引，最好
- `Using where`：索引过滤后还要再行过滤，正常
- `Using filesort`：额外排序，可能缺 `ORDER BY` 对应的索引
- `Using temporary`：用到临时表，通常是 GROUP BY 没走索引
- `Using index condition`：Index Condition Pushdown，MySQL 5.6+ 优化

**第三步：常见优化手段**

```sql
-- 1. 加联合索引，覆盖 WHERE + ORDER BY
ALTER TABLE orders ADD INDEX idx_user_status_created (user_id, status, created_at);

-- 2. 避免 SELECT *
SELECT id, user_id, status, created_at FROM orders WHERE ...;

-- 3. 大分页用延迟关联
SELECT o.* FROM (
    SELECT id FROM orders WHERE user_id = 123 ORDER BY id DESC LIMIT 100000, 10
) t JOIN orders o ON o.id = t.id;

-- 4. COUNT(*) 用覆盖索引
SELECT COUNT(*) FROM orders WHERE user_id = 123;  -- idx_user 存在时很快

-- 5. 批量写入用 INSERT ... VALUES (), (), () 多行语法
```

**performance_schema**：MySQL 5.6+ 内置，可以查哪类操作最耗时：

```sql
-- 某类事件的总耗时
SELECT event_name, count_star, avg_timer_wait/1000000 AS avg_ms
FROM events_summary_by_event_name
ORDER BY sum_timer_wait DESC LIMIT 20;

-- 当前正在执行的 SQL
SELECT * FROM events_statements_current;
```

**排查工具**：`pt-query-digest`（percona 工具包）可以分析慢日志生成报告，比自己 `grep` 快得多。

```bash
pt-query-digest /var/log/mysql/slow.log > report.txt
```

## 11-10 Go 的 context 在超时和取消时的正确用法

**结论**：context 用于在请求链路上传递取消信号、截止时间和请求级数据。HTTP 超时、数据库操作取消、goroutine 泄漏排查都离不开它。

**三个来源函数**：

```go
ctx := context.Background()        // 根 context，永不取消，main 或测试入口用
ctx := context.TODO()              // 占位，不确定用哪个时先写这个
ctx, cancel := context.WithCancel(parent)       // 手动取消
ctx, cancel := context.WithTimeout(parent, 5*time.Second)  // 超时自动取消
ctx, cancel := context.WithDeadline(parent, time.Now().Add(5*time.Second))  // 指定绝对时间
```

**HTTP 超时示例**：

```go
func handler(w http.ResponseWriter, r *http.Request) {
    // 用请求自带的 context，客户端断开会自动传递取消信号
    ctx := r.Context()
    
    // 给 DB 查询加超时
    dbCtx, cancel := context.WithTimeout(ctx, 3*time.Second)
    defer cancel()  // 即使提前返回也要 cancel，释放资源
    
    rows, err := db.QueryContext(dbCtx, "SELECT * FROM orders WHERE user_id = ?", userID)
    if err != nil {
        if errors.Is(err, context.DeadlineExceeded) {
            http.Error(w, "查询超时", http.StatusGatewayTimeout)
            return
        }
        // ...
    }
}
```

**goroutine 泄漏排查**：

```go
func worker(ctx context.Context) {
    for {
        select {
        case <-ctx.Done():
            // 收到取消信号，退出
            fmt.Println("worker stopped:", ctx.Err())
            return
        case job := <-jobCh:
            process(job)
        }
    }
}

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()
    
    go worker(ctx)
    // main 结束后 ctx 会被取消，worker goroutine 也会退出
}
```

**三个坑**：

1. **defer cancel() 不能忘**——WithTimeout 创建的 context 内部起了 timer，不 cancel 会持续到超时，短时间高并发下 timer 堆积
2. **不要把 context 存到 struct 里**——它应该随请求传递，不能被长期持有
3. **context.Value 不要用来传可选参数**——只传请求级的数据（如 request ID、trace ID），业务参数用函数参数传递

**在中间件里传递 trace ID**：

```go
func TraceMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        traceID := r.Header.Get("X-Trace-ID")
        if traceID == "" {
            traceID = uuid.New().String()
        }
        ctx := context.WithValue(r.Context(), "traceID", traceID)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}
```

## 11-10 PHP 用 Redis 存 Session 的配置和坑

**结论**：PHP Session 默认存 `/tmp` 文件，多台应用服务器时无法共享。改成 Redis 后所有节点读写同一份 Session，但要注意锁、过期和序列化三个问题。

**php.ini 配置**：

```ini
# 用 Redis 存 Session
session.save_handler = redis
session.save_path = "tcp://127.0.0.1:6379?database=1"

# 如果有密码
session.save_path = "tcp://127.0.0.1:6379?database=1&auth=your_password"
```

或者在运行时设置（推荐，不需要改 php.ini）：

```php
// 在项目入口文件的最前面
ini_set('session.save_handler', 'redis');
ini_set('session.save_path', 'tcp://127.0.0.1:6379?database=1');
session_start();
```

**Session key 的 Redis 格式**：`PHPREDIS_SESSION:<session_id>`。可以直接在 redis-cli 里查看：

```bash
redis-cli -n 1
> KEYS PHPREDIS_SESSION:*
> GET PHPREDIS_SESSION:abc123def456
```

**三个坑**：

1. **Session 过期时间**：`session.gc_maxlifetime` 决定了 Redis key 的 TTL。默认 1440 秒（24 分钟），用户活跃时应该续期。`session.cookie_lifetime = 0` 表示关闭浏览器就过期，配合 Redis TTL 要一致。

```ini
session.gc_maxlifetime = 7200   # 2 小时
session.cookie_lifetime = 7200  # Cookie 也要同步
```

2. **Session 锁**：PHP 默认开启了 `session_write_close()` 前会阻塞其他请求读同一个 session。同一用户的多个 AJAX 请求会被串行化。可以在 Session 用完后主动释放锁：

```php
session_start();
$_SESSION['user_id'] = 123;
session_write_close();   // 写完就关，让其他请求能继续
// 后面的耗时操作不占 Session 锁
doSomethingSlow();
```

3. **序列化**：默认用 `php` 序列化格式，Redis 里的 value 是 `user_id|i:123;` 这种。如果换成了 `redis` 扩展的 `php_serialize` handler 或者用了 `igbinary`，要确认 PHP 版本和扩展支持。

**Redis 集群注意**：Session 的 key 必须落在同一个 slot 里。因为 `save_path` 只支持单节点，集群模式下应该用代理（如 twemproxy）或者固定一个 Redis 节点存 Session（Session 通常是热点，固定节点性能足够）。

## 11-10 Docker 多阶段构建瘦身镜像

**结论**：构建 Go / PHP / Node 应用的 Docker 镜像时，用多阶段构建可以把最终镜像从几百 MB 降到十几 MB。原理是把编译环境和运行环境分开。

**Go 应用示例**：

```dockerfile
# 第一阶段：编译
FROM golang:1.21-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
# CGO_ENABLED=0 编译纯静态二进制，不需要 libc
# -ldflags="-s -w" 去掉调试信息，再小 30%
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o checksum-tool .

# 第二阶段：运行（alpine 只有 5MB）
FROM alpine:3.19
# Go 应用需要证书才能访问 HTTPS
RUN apk add --no-cache ca-certificates
WORKDIR /app
COPY --from=builder /app/checksum-tool .
EXPOSE 8080
CMD ["./checksum-tool"]
```

镜像对比：

| 方式 | 镜像大小 |
|---|---|
| 直接用 golang:1.21 | ~900MB |
| 多阶段 + alpine | ~15MB |
| distroless (gcr.io/distroless/static) | ~5MB |

**PHP 应用示例**：

```dockerfile
# 构建阶段：安装 composer 依赖
FROM php:8.2-fpm-alpine AS builder
WORKDIR /app
COPY . .
RUN curl -sS https://getcomposer.org/installer | php -- --install-dir=/usr/local/bin --filename=composer
RUN composer install --no-dev --optimize-autoloader --no-interaction

# 运行阶段：只有 PHP + 依赖
FROM php:8.2-fpm-alpine
RUN docker-php-ext-install pdo pdo_mysql redis
WORKDIR /app
COPY --from=builder /app .
RUN chown -R www-data:www-data storage bootstrap/cache
```

**.dockerignore 别忘写**：

```
vendor/
node_modules/
.git/
.gitignore
*.md
.env
.env.local
docker/
tests/
*.log
.DS_Store
```

没写的话 `.git` 目录、`node_modules` 这些会被 COPY 进构建上下文，构建时间和镜像体积都会变大。

**调试用的临时镜像**：

```bash
# 构建并运行，方便进入容器排查问题
docker build -t myapp:debug .
docker run --rm -it myapp:debug sh

# 查看镜像分层，找出哪个层最大
docker history myapp:debug
```

## 11-10 Nginx 的 alias 和 root 路径拼接规则完全不同

**结论**：`root` 把 location 路径拼到 root 后面；`alias` 把 location 路径替换成 alias。静态文件 404 时，先确认用的是哪个。

**对比**

```nginx
# root：最终路径 = root + URI
location /static/ {
    root /var/www;
}
# 请求 /static/app.js → 找文件 /var/www/static/app.js

# alias：location 前缀被替换掉
location /static/ {
    alias /var/www/assets/;
}
# 请求 /static/app.js → 找文件 /var/www/assets/app.js
```

**alias 的两个坑**：

1. **location 和 alias 必须同时带或同时不带尾斜杠**：

```nginx
# 正确
location /static/ { alias /var/www/assets/; }

# 错误：/static/app.js → /var/www/assets//app.js（可能正常也可能异常）
location /static/ { alias /var/www/assets; }

# 错误：/static/app.js → /var/www/assetsapp.js
location /static { alias /var/www/assets/; }
```

2. **alias 不支持 root 那样的路径穿透修改**：alias 只能做前缀替换，不能像 root 那样灵活拼接。复杂场景（如把 `/api/v1/` 映射到 `/opt/app-v1/`）推荐用 `alias`。

**实战对比**：

```nginx
# 场景：把 /images/ 映射到 /data/pictures/

# 用 root 也行，但要建软链
location /images/ {
    root /data;
    # 期望: /images/foo.jpg → /data/images/foo.jpg
}
# 需要手动 ln -s /data/pictures /data/images

# 用 alias 更直接
location /images/ {
    alias /data/pictures/;
    # /images/foo.jpg → /data/pictures/foo.jpg
}
```

**正则 location 里的 alias**：

```nginx
location ~ ^/download/([^/]+)/(.*)$ {
    alias /data/repos/$1/$2;
}
# /download/project-a/v1.0.tar.gz → /data/repos/project-a/v1.0.tar.gz
```

正则 location 里不能用 root（因为正则 location 会捕获 URI 片段，root 不知道怎么拼），但可以用 alias 把捕获组拼到路径里。
